# 食物照片記錄 Agent — 架構文件

## 1. 目標與範圍

使用者在 Discord 私訊裡傳食物照片,Agent 判斷照片內容並存成一筆飲食紀錄。使用者之後可以用自然語言修改、查詢、刪除紀錄,也可以要求為某一筆紀錄產生社群貼文草稿。

第一版範圍(來自需求訪談):

| 項目 | 決定 |
|---|---|
| 主要用途 | 飲食記錄;貼文草稿是附加功能 |
| 每筆紀錄 | 原圖、食物名稱或描述、日期時間、餐別、備註 |
| 不記錄 | 地點、餐廳、營養或熱量、花費(照片無法可靠判斷) |
| 使用者 | 紀錄依使用者分開;第一版只開放作者的 Discord 帳號 |
| 互動範圍 | 只在 DM 回覆,不在公開頻道回覆 |
| 查詢 | 某一天、某一餐別、最近幾天 |
| 不做 | 網頁介面、多筆合併貼文、草稿存檔、自動發佈、社群帳號連結 |

## 2. 使用者體驗

### 2.1 傳照片

1. 使用者傳一張或多張照片,可附一句話。
2. Agent 立刻回「收到,處理中」。
3. 處理完回一則確認摘要,每張照片各一則:
   - 食物名稱、日期時間、餐別、備註
   - **照片中看得到的**與 **AI 推測的**分開列出
4. 附的那句話存成備註。若那句話同時指定餐別(例如「午餐,很好吃」),餐別採用指定值。

### 2.2 認不出或不是食物

- 不是食物:不保存,回覆說明原因。
- 是食物但認不出:回「這是什麼?」。使用者回答後,以回答作為食物名稱並存檔。

### 2.3 修改、查詢、刪除、草稿

全部用自然語言,不需要記指令。

| 意圖 | 範例 |
|---|---|
| 修改 | 「把剛剛那張改成晚餐」「幫我加上備註很好吃」 |
| 查詢 | 「我昨天吃了什麼」「這週的晚餐有哪些」 |
| 刪除 | 「刪掉剛剛那張」「刪掉昨天的晚餐」→ Agent 先確認,同意後永久刪除紀錄與原圖 |
| 草稿 | 「幫我寫剛剛那張的貼文」「寫成 TikTok、英文」 |

貼文草稿預設:繁體中文、Instagram、輕鬆語氣;一次產出三個影片開頭、一篇文案、一組 hashtag。草稿不存檔。

### 2.4 等待與出錯

- 處理中先回「收到」。
- AI 呼叫失敗時,告知使用者「照片已先保存,稍後會再試」,不需要重傳。
- Agent 離線期間傳的照片,恢復上線後自動補處理。

## 3. 系統總覽

```
 使用者 (Discord DM)
        │  訊息 / 照片
        ▼
┌──────────────────┐
│  Discord Bot     │  收訊息、白名單檢查、回覆「收到」
│  (discord.py)    │
└────────┬─────────┘
         │ 寫入 jobs
         ▼
┌──────────────────┐        ┌──────────────────────┐
│  SQLite          │◄──────►│  Worker (單一執行緒) │
│  jobs / records  │        │  依序處理 jobs       │
│  / pending       │        └───────┬──────────────┘
└──────────────────┘                │
         ▲                          │ subprocess
         │                          ▼
┌──────────────────┐        ┌──────────────────────┐
│  photos/<user>/  │        │  claude -p           │
│  原圖檔案        │        │  (唯讀、無網路工具)  │
└──────────────────┘        └──────────────────────┘
```

語言與主要套件:Python 3、`discord.py`、標準庫 `sqlite3`、`Pillow`(讀 EXIF)。

選擇理由:
- **discord.py**:最成熟的 Python Discord 套件,支援 DM、附件下載、讀取歷史訊息(補處理要用)。
- **SQLite**:單人使用、資料量小,不需要另外架資料庫;單一檔案好備份;同時拿來當工作佇列。
- **claude -p**:不需要另外申請 API 金鑰與計費,符合「避免不必要的付費 API」;非互動模式可以被程式呼叫,能讀本機圖片檔。

## 4. 元件

### 4.1 Discord Bot(`bot/`)

- 只處理 DM,且作者 ID 必須在白名單 `ALLOWED_USER_IDS`,其他一律忽略(不回覆,避免洩漏 Bot 存在與耗用額度)。
- 收到訊息就寫進 `jobs`,再回「收到,處理中」。Bot 本身不做任何 AI 或耗時工作,所以不會卡住 Discord 連線。
- Worker 完成後,由 Bot 把結果傳回同一個 DM。

### 4.2 Worker(`worker/`)

- 單一 worker 迴圈,從 `jobs` 取最舊的 `queued` 工作處理。
- 單一 worker 是刻意的:一個使用者、`claude -p` 每次要數秒到數十秒,序列處理最簡單,也保證「剛剛那張」的順序正確。

### 4.3 AI 呼叫層(`ai/`)

把 `claude -p` 包成幾個純函式,其他程式碼不直接碰 subprocess:

| 函式 | 輸入 | 輸出(JSON) |
|---|---|---|
| `analyze_photo` | 圖片路徑 | `is_food`、`food_name`、`observed[]`、`inferred[]`、`identifiable` |
| `interpret_message` | 使用者文字、必要上下文 | `intent`(`edit`/`query`/`delete`/`draft`/`other`)與結構化參數 |
| `write_draft` | 單筆紀錄、平台、語氣、語言 | `hooks[3]`、`caption`、`hashtags[]` |

呼叫方式:`claude -p` 非互動模式、要求 JSON 輸出、只允許讀取圖片所需的工具、限制回合數、設定逾時。實作時要以實際安裝的 Claude Code 版本確認旗標名稱。

### 4.4 儲存層(`store/`)

提供紀錄的新增、修改、查詢、刪除。所有函式都必須帶 `user_id`,資料層不提供「不指定使用者」的查詢,從結構上避免跨使用者讀取。

## 5. 資料模型

### `records`

| 欄位 | 說明 |
|---|---|
| `id` | 主鍵 |
| `user_id` | Discord 使用者 ID |
| `photo_path` | 原圖相對路徑 |
| `food_name` | 食物名稱或描述 |
| `observed` | 照片中看得到的(JSON 陣列) |
| `inferred` | AI 推測的(JSON 陣列) |
| `taken_at` | 時間(UTC) |
| `time_source` | `exif` 或 `upload` |
| `meal_type` | `早餐`/`午餐`/`晚餐`/`點心` |
| `meal_source` | `user`(使用者指定或修改)或 `auto`(依時間判斷) |
| `note` | 備註 |
| `created_at` | 建立時間 |

### `jobs`

| 欄位 | 說明 |
|---|---|
| `id` | 主鍵 |
| `user_id` | 使用者 |
| `discord_message_id` | 訊息 ID |
| `attachment_id` | 附件 ID,文字訊息為空 |
| `kind` | `photo` 或 `text` |
| `payload` | 文字內容或暫存圖片路徑 |
| `status` | `queued`/`running`/`done`/`failed` |
| `attempts` | 已重試次數 |
| `created_at` | 時間 |

`(discord_message_id, attachment_id)` 設唯一限制,補處理時不會重複建立。

### `pending`

記錄「Agent 在等使用者回答」的狀態,每個使用者同時最多一筆:

| 欄位 | 說明 |
|---|---|
| `user_id` | 使用者 |
| `type` | `food_name`(等使用者說這是什麼)或 `delete_confirm`(等使用者確認刪除) |
| `ref` | 對應的暫存照片或紀錄 ID |
| `expires_at` | 逾時時間 |

### `bot_state`

存「最後處理到的 Discord 訊息 ID」,補處理時用。

### 檔案

```
data/
  app.db
  photos/<user_id>/<YYYY>/<MM>/<record_id>.jpg
  inbox/<user_id>/<attachment_id>.jpg   ← 尚未處理完的暫存照片
```

## 6. 主要流程

### 6.1 傳照片

1. Bot 下載附件到 `inbox/`,寫入 `jobs`(`queued`),回「收到,處理中」。
2. Worker 取出工作,呼叫 `analyze_photo`。
3. 判斷:
   - `is_food = false`:刪除暫存檔,回覆「這不是食物,沒有記錄」。
   - `identifiable = false`:寫入 `pending(food_name)`,回「這是什麼?」。暫存檔保留。
   - 其他:進入第 4 步。
4. 決定時間:讀 EXIF 拍攝時間,讀不到才用 Discord 訊息時間;`time_source` 如實記錄。
5. 決定餐別:使用者文字指定 > 依時間判斷(見 6.6)。
6. 把照片從 `inbox/` 移到 `photos/`,寫入 `records`,回確認摘要。

多張照片會拆成多個 job,各自完成各自回覆。

### 6.2 使用者回答「這是什麼?」

下一則文字訊息先檢查 `pending`:若有 `food_name`,把這則文字當食物名稱,走 6.1 的第 4 到 6 步存檔。逾時未回答則丟棄暫存照片並清除 pending。

### 6.3 修改

`interpret_message` 回傳 `intent = edit` 與欄位、新值、目標。目標預設是「最近一筆」,也可以指定日期與餐別。程式驗證欄位在可修改範圍內(食物名稱、餐別、備註)後才寫入。使用者改餐別時,`meal_source` 設為 `user`。

### 6.4 查詢

AI 只負責把問題轉成結構化條件(日期範圍、餐別),**由程式組 SQL 並執行**,AI 不寫也不執行 SQL。結果用固定格式列出,並依需要附上照片。

### 6.5 刪除

1. 解析出目標紀錄(最近一筆或指定日期與餐別)。目標不唯一時列出候選,請使用者指定。
2. 寫入 `pending(delete_confirm)`,回「要刪除『雞肉便當,午餐』嗎?」。
3. 使用者確認後,同一個交易內刪除資料列,並刪除原圖檔。
4. 使用者否認或逾時,取消。

### 6.6 餐別判斷

只有使用者沒有指定餐別時才依時間判斷,時間用台灣時間(Asia/Taipei):

| 時段 | 餐別 |
|---|---|
| 05:00 – 10:30 | 早餐 |
| 10:30 – 14:30 | 午餐 |
| 14:30 – 17:00 | 點心 |
| 17:00 – 21:00 | 晚餐 |
| 21:00 – 05:00 | 點心(含宵夜) |

回覆摘要會註明「依時間判斷」,使用者不同意就能直接改。

### 6.7 貼文草稿

1. 解析出目標紀錄、平台、語氣、語言;沒指定的用預設值。
2. 只把該筆紀錄的食物名稱、`observed`、`inferred` 與備註交給 `write_draft`。
3. 輸出經過驗證後直接回覆,不存檔。

## 7. 排隊與補處理

**排隊**:`jobs` 資料表就是佇列。Bot 只寫入、Worker 只讀取並更新狀態,兩者不直接互相呼叫。程式崩潰時,狀態為 `running` 的工作在下次啟動時改回 `queued`。

**失敗重試**:`claude -p` 逾時或回傳錯誤時,`attempts` 加一,以遞增間隔重試,最多 3 次;超過就標記 `failed` 並通知使用者。照片留在 `inbox/`,不會遺失。

**離線補處理**:
1. Bot 啟動時,讀 `bot_state` 的最後訊息 ID。
2. 用 Discord 的歷史訊息 API 抓取該 ID 之後、該使用者 DM 裡的所有訊息。
3. 逐一寫入 `jobs`;唯一限制讓重複的訊息被忽略。
4. 時間以照片 EXIF 或原始訊息時間為準,不是補處理當下的時間,所以日期與餐別不會錯。

Discord 上傳圖片時可能會移除 EXIF,所以實際上常會用到「上傳時間」這個後備方案。這點要在實作時實測確認。

## 8. 輸入清洗與安全

使用者的文字、備註、圖片都是**資料,不是指令**。

| 風險 | 對策 |
|---|---|
| 提示注入(照片中的字或使用者訊息夾帶「忽略之前的指令」) | 系統指令與使用者內容分開傳遞;使用者內容用明確的分隔標記包起來;`claude -p` 只開放讀圖所需的最小工具,不開放寫檔與執行命令,即使被騙也做不了壞事 |
| AI 輸出格式錯誤或內容越界 | 輸出一律當 JSON 解析並驗證欄位、型別、長度與列舉值;驗證失敗視為呼叫失敗,走重試 |
| 惡意或損壞的圖片 | 檢查副檔名與實際內容類型、限制檔案大小與像素數;用 Pillow 重新編碼為 JPEG 後才存檔,同時丟棄多餘的中繼資料 |
| 路徑穿越 | 檔名完全由程式產生(使用者 ID 與紀錄 ID),不使用任何使用者提供的檔名 |
| SQL 注入 | 一律使用參數化查詢;AI 不產生 SQL |
| 陌生人使用 | 白名單;非白名單的訊息直接忽略 |
| 密鑰外洩 | Discord Token 放環境變數或 `.env`,`.env` 加入 `.gitignore` |
| 過長文字 | 備註與食物名稱限制長度,超過就截斷並告知使用者 |

## 9. 誠實規則

來自 `docs/requirements.md` 的限制,實作在提示詞與輸出驗證兩層:

- 紀錄分成 `observed`(看得到的)與 `inferred`(推測的),確認摘要分開顯示。
- 認不出就回 `identifiable = false`,由使用者回答,不猜。
- 不產出價格、食材清單、營養、餐廳名稱等照片無法證明的資訊,除非使用者自己寫在備註裡。
- 貼文草稿只使用紀錄裡已有的內容。

## 10. 錯誤處理

| 狀況 | 行為 |
|---|---|
| `claude -p` 逾時或失敗 | 照片保留,重試最多 3 次,第一次失敗就通知使用者「稍後會再試」 |
| AI 輸出無法解析 | 視同失敗,走重試 |
| 圖片下載失敗 | 回覆請使用者重傳(這是唯一需要重傳的情況) |
| 無法判斷意圖 | 回覆簡短說明可以做哪些事 |
| 修改或刪除找不到目標 | 回覆沒找到,列出最近幾筆讓使用者選 |
| Bot 離線 | 見第 7 節補處理 |
| 資料庫寫入失敗 | 交易回滾,不刪原圖暫存,通知使用者 |

## 11. 測試策略

- **單元測試**:餐別判斷、EXIF 與上傳時間的取捨、輸出驗證、清洗函式、SQL 條件組裝。這些都是純邏輯,不需要真的呼叫 AI。
- **AI 呼叫層**:用假的 subprocess 回傳固定 JSON,測試成功、格式錯誤、逾時、重試。
- **整合測試**:用假的 Discord 事件與暫存資料庫,跑完整流程(傳照片、認不出、修改、查詢、刪除確認、補處理去重)。
- **少量真實呼叫**:手動用幾張樣本照片確認 `claude -p` 的實際輸出符合格式,不放進自動化測試以免耗用額度。

需求文件要求遵守講師指定的開發與測試流程。目前沒有看到具體規定,若有(例如先寫測試再寫程式),實作計畫要按那個流程排序。

## 12. 專案結構

```
bot/        Discord 事件處理、白名單、回覆
worker/     佇列迴圈、流程編排
ai/         claude -p 包裝、提示詞、輸出驗證
store/      SQLite 存取、檔案存放
sanitize/   圖片與文字清洗
tests/
data/       執行時產生,不進版本控制
docs/
```

## 13. 主要決策與取捨

| 決策 | 理由 | 取捨 |
|---|---|---|
| `claude -p` 而不是 API | 不另外計費 | 每次呼叫要啟動程序,延遲較高;依賴本機有安裝與登入 |
| 單一 worker | 簡單且順序正確 | 多人使用時會變慢,第一版只有一人 |
| SQLite 當佇列 | 不用另外架服務,崩潰後可恢復 | 不適合高流量,但這裡用不到 |
| AI 不產生 SQL | 避免注入與越權 | 查詢種類受限於程式支援的條件 |
| 非食物照片不保存 | 紀錄乾淨 | 誤判的食物照片需要使用者重傳 |
| 資料依使用者分開 | 隱私,日後開放給他人不用改結構 | 每個查詢都要帶 `user_id` |
| 只在 DM 回覆 | 飲食紀錄屬於個人隱私 | 無法在群組裡使用 |

## 14. 未解決的問題

- Discord 是否移除圖片 EXIF,需要實測;若幾乎都移除,「拍攝時間」就幾乎都是上傳時間,補傳舊照片的日期要靠使用者自己說明。
- 使用者長時間不回答「這是什麼?」時,暫存保留多久(暫定 24 小時)。
- `claude -p` 的實際旗標與輸出格式,要在實作第一步用安裝的版本驗證。
- 資料備份:第一版沒有自動備份,`data/` 目錄建議使用者自行定期備份。
