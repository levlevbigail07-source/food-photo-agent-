# 食物照片內容創作 Agent — 架構文件

## 1. 目標與範圍

使用者在 Discord 私訊裡傳一張食物或飲料照片,Agent 看圖後產生可直接用在社群的內容:

- 食物描述
- 三個短影音開頭
- 一篇社群貼文文案
- 一組 hashtag
- (選用)內容角度或創意點子

內容會依使用者的平台、受眾、語言、語氣調整。Agent 不發佈任何東西,只回覆文字,使用者自己複製使用。

第一版範圍(來自需求文件與訪談):

| 項目 | 決定 |
|---|---|
| 主要用途 | 照片 → 社群內容 |
| 主要題材 | 食物與飲料;其他物品不主動拒絕,照樣產生內容 |
| 偏好 | 平台、受眾、語言、語氣;每位使用者有自己的預設值,也可以在訊息中臨時覆蓋 |
| 使用者 | 偏好依使用者分開;第一版只開放作者的 Discord 帳號 |
| 互動範圍 | 只在 DM 回覆,不在公開頻道回覆 |
| 歷史 | **不保存**照片與產生結果,只保留運作必要的資料(見第 5 節) |
| 不做 | 飲食日記、餐別判斷、查詢、熱量或營養估計、網頁介面、自動發佈、社群帳號連結、付費 API |

## 2. 使用者體驗

### 2.1 傳照片

1. 使用者傳一張或多張照片,可附一句話(例如「這次用 TikTok、英文」或「這是我自己做的拿鐵」)。
2. Agent 立刻回「收到,處理中」。
3. 處理完,每張照片各回一則結果:
   - **描述**:分成「照片中看得到的」與「推測的」
   - **三個短影音開頭**
   - **貼文文案**
   - **hashtag**
   - **內容角度**(選用)
4. 結果超過 Discord 單則訊息長度上限時,自動拆成多則,順序固定。

### 2.2 偏好

| 項目 | 預設值 | 說明 |
|---|---|---|
| 平台 | Instagram | TikTok、Instagram、YouTube Shorts,或使用者自訂的其他平台 |
| 受眾 | 喜歡美食的一般社群追蹤者 | 使用者可改成「上班族」「學生」「健身族群」等 |
| 語言 | 繁體中文 | |
| 語氣 | 輕鬆自然 | |

- **臨時覆蓋**:寫在傳照片的那則訊息裡,只對這次有效。例如「這次用 TikTok、英文」。
- **改預設**:用自然語言說,例如「以後預設用 YouTube Shorts」「我的預設受眾改成上班族」。
- **查看**:「我現在的偏好是什麼?」
- 訊息說得不夠明確、分不出是「這次」還是「以後」時,視為「這次」,並問一句要不要設為預設。

### 2.3 照片看不清楚或不是食物

- 看不出是什麼:Agent 誠實說明,只根據看得到的部分產生內容(例如「一碗看起來像湯的料理」),並提醒使用者可以回覆名稱,下一張照片時附上名稱即可。不編造菜名。
- 不是食物或飲料:照樣處理,以看得到的物品為題材產生內容,不拒絕。
- 照片幾乎沒有內容(全黑、完全模糊):回覆無法辨識,請使用者換一張。

### 2.4 等待與出錯

- 處理中先回「收到」。
- AI 呼叫失敗時,告知使用者「照片已先保存,稍後會再試」,不需要重傳。
- 重試仍失敗(最多 3 次),通知使用者並請重傳。
- Agent 離線期間傳的訊息,恢復上線後自動補處理,回覆時註明這是補處理。

## 3. 系統總覽

```
 使用者 (Discord DM)
        │  訊息 / 照片
        ▼
┌──────────────────┐
│  Discord Bot     │  收訊息、白名單檢查、回覆「收到」
│  (discord.py)    │
└────────┬─────────┘
         │ 寫入 jobs
         ▼
┌──────────────────┐        ┌──────────────────────┐
│  SQLite          │◄──────►│  Worker (單一執行緒) │
│  jobs            │        │  依序處理 jobs       │
│  user_preferences│        └───────┬──────────────┘
└──────────────────┘                │ subprocess
         ▲                          ▼
┌──────────────────┐        ┌──────────────────────┐
│  data/inbox/     │        │  claude -p           │
│  處理中的暫存照片│        │  (唯讀、無網路工具)  │
└──────────────────┘        └──────────────────────┘
```

語言與主要套件:Python 3、`discord.py`、標準庫 `sqlite3`、`Pillow`(檢查與重新編碼圖片)。

選擇理由:
- **discord.py**:最成熟的 Python Discord 套件,支援 DM、附件下載、讀取歷史訊息(補處理要用)。
- **SQLite**:單人使用、資料量小,不需要另外架資料庫;單一檔案好備份;同時拿來當工作佇列。
- **claude -p**:不需要另外申請 API 金鑰與計費,符合需求文件「避免不必要的付費 API」;非互動模式可以被程式呼叫,能讀本機圖片檔。

## 4. 元件

### 4.1 Discord Bot(`bot/`)

- 只處理 DM,且作者 ID 必須在白名單 `ALLOWED_USER_IDS`,其他一律忽略(不回覆,避免洩漏 Bot 存在與耗用額度)。
- 收到訊息就寫進 `jobs`,再回「收到,處理中」。Bot 本身不做 AI 或耗時工作,所以不會卡住 Discord 連線。
- Worker 完成後,由 Bot 把結果傳回同一個 DM,必要時拆成多則。

### 4.2 Worker(`worker/`)

- 單一 worker 迴圈,從 `jobs` 取最舊的 `queued` 工作處理。
- 單一 worker 是刻意的:一個使用者、`claude -p` 每次要數秒到數十秒,序列處理最簡單,也保證回覆順序與傳送順序一致。

### 4.3 AI 呼叫層(`ai/`)

把 `claude -p` 包成兩個純函式,其他程式碼不直接碰 subprocess:

| 函式 | 輸入 | 輸出(JSON) |
|---|---|---|
| `interpret_message` | 使用者文字 | `intent`(`set_default`/`show_prefs`/`generate`/`other`)、偏好覆蓋值(`platform`/`audience`/`language`/`tone`)、`scope`(`once`/`default`)、`context_note`(使用者提供的補充,例如「這是我自己做的拿鐵」) |
| `generate_content` | 圖片路徑、生效的偏好、`context_note` | `subject_type`(`food`/`drink`/`other`)、`identifiable`、`observed[]`、`inferred[]`、`hooks[3]`、`caption`、`hashtags[]`、`angles[]` |

- 傳照片時若沒附文字,跳過 `interpret_message`,直接用預設偏好。
- `interpret_message` 只有文字,速度快;`generate_content` 才需要看圖。
- 呼叫方式:`claude -p` 非互動模式、要求 JSON 輸出、只開放讀取圖片所需的工具、限制回合數、設定逾時。實作時要以實際安裝的 Claude Code 版本確認旗標名稱。
- 平台差異(長度、語氣、hashtag 習慣)放在提示詞裡的平台說明,不寫死在程式。

### 4.4 儲存層(`store/`)

只管兩件事:使用者偏好的讀寫、工作佇列的讀寫。所有函式都必須帶 `user_id`。

## 5. 資料模型

第一版不保存歷史,所以只有三張表,沒有任何紀錄、照片庫或產生結果。

### `user_preferences`

| 欄位 | 說明 |
|---|---|
| `user_id` | Discord 使用者 ID(主鍵) |
| `platform` | 預設平台 |
| `audience` | 預設受眾 |
| `language` | 預設語言 |
| `tone` | 預設語氣 |
| `updated_at` | 更新時間 |

沒有這一列時使用第 2.2 節的預設值。

### `jobs`

| 欄位 | 說明 |
|---|---|
| `id` | 主鍵 |
| `user_id` | 使用者 |
| `discord_message_id` | 訊息 ID |
| `attachment_id` | 附件 ID,純文字訊息為空 |
| `kind` | `photo` 或 `text` |
| `payload` | 使用者文字,或暫存圖片路徑 |
| `status` | `queued`/`running`/`done`/`failed` |
| `attempts` | 已重試次數 |
| `created_at` | 時間 |

- `(discord_message_id, attachment_id)` 設唯一限制,補處理時不會重複建立。
- 工作完成或最終失敗後,`payload` 清空;整列保留 7 天後刪除。保留是為了去重,不是為了留紀錄。

### `bot_state`

存「最後處理到的 Discord 訊息 ID」,補處理時用。

### 檔案

```
data/
  app.db
  inbox/<user_id>/<attachment_id>.jpg   ← 只存處理中的照片
```

照片在工作成功或最終失敗後立即刪除。產生的內容只存在 Discord 對話裡,不在本機留存。

## 6. 主要流程

### 6.1 傳照片(含文字)

1. Bot 下載附件到 `inbox/`,寫入 `jobs`(`queued`),回「收到,處理中」。
2. Worker 取出工作。若同一則訊息附有文字,呼叫 `interpret_message`:
   - `intent = generate`:取出覆蓋值與 `context_note`。
   - 其他 intent:依 6.3 處理,照片仍照常產生內容。
3. 決定生效偏好:臨時覆蓋 > 使用者預設 > 系統預設,逐欄位決定。
4. 呼叫 `generate_content`,驗證輸出(見第 8 節)。
5. 組成回覆(必要時拆多則),傳回 DM。
6. 刪除暫存照片,工作標記 `done`。

多張照片拆成多個 job,各自完成各自回覆。

### 6.2 純文字訊息

呼叫 `interpret_message`:

| intent | 動作 |
|---|---|
| `set_default` | 更新 `user_preferences`,回覆新的預設值 |
| `show_prefs` | 回覆目前生效的偏好 |
| `generate` 但沒有照片 | 回覆「請傳一張照片」 |
| `other` | 簡短說明可以做什麼 |

### 6.3 偏好的優先順序

```
本次訊息的臨時覆蓋  >  使用者預設(user_preferences)  >  系統預設
```

臨時覆蓋不寫入資料庫。`scope = default` 時才更新 `user_preferences`。

## 7. 排隊與補處理

**排隊**:`jobs` 資料表就是佇列。Bot 只寫入、Worker 只讀取並更新狀態,兩者不直接互相呼叫。程式崩潰時,狀態為 `running` 的工作在下次啟動時改回 `queued`。

**失敗重試**:`claude -p` 逾時或回傳錯誤時,`attempts` 加一,以遞增間隔重試,最多 3 次。第一次失敗就通知使用者「照片已先保存,稍後會再試」;超過 3 次標記 `failed`,通知使用者並請重傳,同時刪除暫存照片。

**離線補處理**:
1. Bot 啟動時,讀 `bot_state` 的最後訊息 ID。
2. 用 Discord 的歷史訊息 API 抓取該 ID 之後、該使用者 DM 裡的訊息。
3. 依時間順序寫入 `jobs`;唯一限制讓重複的訊息被忽略。
4. 回覆時註明「離線期間收到,現在補處理」。
5. 純文字訊息也照順序補處理,所以離線期間下的「以後預設用 TikTok」會在之後的照片之前生效。

## 8. 輸入清洗與安全

使用者的文字、圖片(包含圖片裡的文字)都是**資料,不是指令**。

| 風險 | 對策 |
|---|---|
| 提示注入(照片中的字或使用者訊息夾帶「忽略之前的指令」) | 系統指令與使用者內容分開傳遞;使用者內容用明確的分隔標記包起來;`claude -p` 只開放讀圖所需的最小工具,不開放寫檔與執行命令,即使被騙也做不了壞事 |
| AI 輸出格式錯誤或內容越界 | 輸出一律當 JSON 解析並驗證欄位、型別、長度與列舉值(`hooks` 必須剛好三個、`hashtags` 不可為空、`platform` 要在已知清單或為合理的自訂值);驗證失敗視為呼叫失敗,走重試 |
| 偏好值被塞入惡意內容 | `platform`、`audience`、`tone` 限制長度與字元;只當作提示詞裡的資料欄位,不拼進指令 |
| 惡意或損壞的圖片 | 檢查副檔名與實際內容類型、限制檔案大小與像素數;用 Pillow 重新編碼為 JPEG 後才交給 AI,同時丟棄 EXIF 等中繼資料(其中可能含 GPS 位置) |
| 路徑穿越 | 暫存檔名完全由程式產生(使用者 ID 與附件 ID),不使用任何使用者提供的檔名 |
| SQL 注入 | 一律使用參數化查詢 |
| 陌生人使用 | 白名單;非白名單的訊息直接忽略 |
| 密鑰外洩 | Discord Token 放環境變數或 `.env`,`.env` 已在 `.gitignore` |
| Discord 訊息長度 | 單則上限約 2000 字,回覆自動拆分 |

## 9. 誠實規則

來自 `docs/requirements.md` 的限制,實作在提示詞與輸出驗證兩層:

- 描述分成 `observed`(看得到的)與 `inferred`(推測的),回覆時分開顯示。
- 認不出就回 `identifiable = false`,只描述看得到的外觀,不猜菜名。
- 不編造菜名、品牌、價格、食材、產地、營養或熱量,以及「健康」「低卡」等健康宣稱,除非使用者自己在訊息裡提供。
- 使用者提供的補充(`context_note`)可以用在內容裡,但視為「使用者說的」,不當成照片中看到的事實。
- 影片開頭與文案不使用無法證明的誇大說法(例如「全台最好吃」)。

## 10. 錯誤處理

| 狀況 | 行為 |
|---|---|
| `claude -p` 逾時或失敗 | 照片保留,重試最多 3 次,第一次失敗就通知使用者 |
| AI 輸出無法解析或驗證失敗 | 視同失敗,走重試 |
| 圖片下載失敗或檔案無效 | 回覆請使用者重傳 |
| 訊息無法判斷意圖 | 回覆簡短說明可以做哪些事 |
| 偏好值無效(例如空白或過長) | 回覆原因,不更新,沿用原本的偏好 |
| Bot 離線 | 見第 7 節補處理 |
| 資料庫寫入失敗 | 交易回滾,保留暫存照片,通知使用者 |

## 11. 測試策略

- **單元測試**:偏好優先順序(臨時 > 使用者預設 > 系統預設)、輸出驗證(三個開頭、hashtag、欄位長度)、圖片清洗、訊息拆分、去重。這些都是純邏輯,不需要真的呼叫 AI。
- **AI 呼叫層**:用假的 subprocess 回傳固定 JSON,測試成功、格式錯誤、逾時、重試。
- **整合測試**:用假的 Discord 事件與暫存資料庫,跑完整流程(傳照片、附文字覆蓋、改預設、認不出、失敗重試、補處理去重、處理完刪除暫存照片)。
- **少量真實呼叫**:手動用幾張樣本照片確認 `claude -p` 的實際輸出符合格式,並檢查有沒有編造事實;不放進自動化測試,以免耗用額度。

需求文件要求遵守講師指定的開發與測試流程。目前沒有看到具體規定,若有(例如先寫測試再寫程式),實作計畫要按那個流程排序。

## 12. 專案結構

```
bot/        Discord 事件處理、白名單、回覆與拆分
worker/     佇列迴圈、流程編排、偏好優先順序
ai/         claude -p 包裝、提示詞、輸出驗證
store/      SQLite 存取(偏好、佇列)
sanitize/   圖片與文字清洗
tests/
data/       執行時產生,不進版本控制
docs/
```

## 13. 主要決策與取捨

| 決策 | 理由 | 取捨 |
|---|---|---|
| 不保存歷史 | 貼近目標、結構最簡單、隱私風險最低 | 使用者無法回頭重看舊內容,要自己從 Discord 對話找 |
| `claude -p` 而不是 API | 不另外計費 | 每次呼叫要啟動程序,延遲較高;依賴本機有安裝與登入 |
| 單一 worker | 簡單且回覆順序正確 | 多人使用時會變慢,第一版只有一人 |
| SQLite 當佇列 | 不用另外架服務,崩潰後可恢復 | 不適合高流量,這裡用不到 |
| 兩次 AI 呼叫(解讀文字、產生內容) | 文字解讀很快,職責分開好驗證 | 附文字的照片多一次呼叫 |
| 偏好每位使用者各一份 | 日後開放給他人不用改結構 | 每個查詢都要帶 `user_id` |
| 其他物品不拒絕 | 與需求文件的「各類日常物品」一致 | 非食物題材的內容品質沒有針對性調校 |
| 只在 DM 回覆 | 保持個人化,不打擾公開頻道 | 無法在群組裡使用 |

## 14. 未解決的問題

- 使用者想「換成 TikTok 版本」重新產生,目前需要重傳照片,因為照片處理完就刪除。若覺得不方便,可以另外加「只保留最近一張照片 24 小時」,第一版先不做。
- 預設受眾的措辭(目前是「喜歡美食的一般社群追蹤者」)要在實測後調整。
- 各平台的提示詞說明(長度、hashtag 數量習慣)要實測後再定,文件不寫死數字。
- `claude -p` 的實際旗標、輸出格式,以及是否能直接讀取本機圖片路徑,要在實作第一步用安裝的版本驗證。
- 第一版沒有備份需求(沒有歷史資料),只有偏好表,遺失可以重設。
